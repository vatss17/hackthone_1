## B. Review by required inspection area

1. **Effective privileges.** `anon`: none on any new table (checked: zero rows in `role_table_grants`). `authenticated`: SELECT everywhere; INSERT/UPDATE only on the listed columns; DELETE only on the five link-style tables; reference tables SELECT only. Verified locally by behaviour (column-denied statements return `42501`). `service_role`: keeps Supabase's default full access (decision 9); the application never uses it.
2. **RLS.** Enabled (not forced) on all ten tables. Read: member or platform admin. Write: owner via `private.is_org_owner`. Independent records' UPDATE policy also requires `archived_at is null` on the existing row.
3. **Foreign keys.** All parent relationships are composite and organization-scoped; reference FKs are plain, `on delete restrict`. Cross-company links are refused by the constraint itself (`23503`) in addition to RLS (`42501`). Tested for machines, specifications, links and certificates.
4. **Uniqueness and NULL behaviour.** Partial unique indexes: reference or custom process/material once per factory or product (case-insensitive custom names), one factory-wide capacity row per factory, active product name and internal code per company, certificate (issuer, number) among active rows, spec name per product, factory-product pair. NULLs never collide in the partial indexes (tested: two products without a code). Nullable composite FK on certifications (see design doc section 2).
5. **Archive behaviour.** Documented and enforced (design doc section 7). Frozen dependents (`55000`), no API restore, name reuse after archive: all tested locally.
6. **Audit compatibility.** The existing `private.audit_row_change()` works unchanged for all eight tables (it reads `organization_id` and `id`); insert, update and delete were all recorded with the acting user; rows contain no business values; every row is attributed to the correct company.
7. **Concurrent inserts and duplicate prevention** (full analysis in section E). Duplicates are prevented by unique indexes, which are race-safe. The composition cap serializes on the parent product row (`FOR NO KEY UPDATE`); the archive-freeze check locks the parent `FOR SHARE`. Lock order is consistent (`a_composition_total` fires before `b_active_parents`; strongest lock first) to avoid a share-then-update upgrade deadlock. **Not tested** (single connection locally): see checklist C6.
8. **Service-role assumptions.** No service-role call is added to the application. Triggers run as the definer, not as `service_role`. The new tables inherit Supabase's default `service_role` access; see decision 9.
9. **SECURITY DEFINER exposure.** Two new functions, both trigger functions in schema `private` (not exposed by the Data API), `search_path = ''`, EXECUTE revoked from PUBLIC, `anon` and `authenticated` (checked locally with `has_function_privilege` and the ACL). Neither takes caller input; they read only `archived_at` or the shares of rows addressed by the caller's own `(organization_id, id)` pair, so they disclose nothing across companies.
10. **Isolation by organization.** Every tenant table has `organization_id`, composite FKs, and owner/member RLS. Locally, user B saw zero rows of A's data in all eight tenant tables, could not update or delete A's rows, could not link A's parents, and anon could read nothing.

## E. Composition concurrency: analysis and test plan

**Function:** `private.enforce_composition_total()`, a BEFORE trigger on `product_materials` (INSERT, or UPDATE of `share_percent` or `product_id`).

**Mechanism:** lock the parent `products` row `FOR NO KEY UPDATE`, then `SELECT sum(share_percent)` of the product's other rows, then compare.

| Question | Analysis |
|---|---|
| Two concurrent inserts of 60 percent | The second blocks on the product row lock until the first commits. Its `SUM` is a new statement taken after the lock is granted, so under READ COMMITTED it sees the first row and is refused (`23514`). Exactly one succeeds. |
| Concurrent updates of two existing rows (40 to 60 each) | Same: serialized by the lock; the second sees the other's committed 60 and is refused. |
| Why `FOR NO KEY UPDATE` | It conflicts with itself (serializes composition edits) and with archiving the product, but not with `FOR KEY SHARE`, so unrelated inserts that only reference the product (specifications, links, certificates) are not blocked. `FOR UPDATE` would have blocked them. |
| Isolation assumptions | **READ COMMITTED** (PostgREST/Supabase default): correct as above. **REPEATABLE READ**: the snapshot is fixed at the first statement, so the sum could be stale even after waiting: the trigger **refuses** that level (`25000`) instead of checking unreliably. **SERIALIZABLE**: correct (lock plus PostgreSQL's conflict detection). |
| Deadlocks | All paths lock the product row strongest-first: `a_composition_total` (NO KEY UPDATE) fires before `b_active_parents` (SHARE on the same row, already held: no upgrade). The FK check takes `KEY SHARE`, weaker than what is already held. A cycle needs two sessions locking different rows in opposite order within one transaction; the API runs one statement per transaction. If one ever happened PostgreSQL would abort one session (`40P01`), never corrupt data. One theoretical order: a single transaction that archives a product then a factory, racing a link insert (factory then product); ordinary API calls cannot do that. |
| Known limit | A multi-row UPDATE is validated row by row, so a change valid only as a set (a swap through an over-100 intermediate state) can be refused. The app edits one row per request. |
| Gap closed in this revision | A row moved to another product (`product_id` updated, possible only for the database owner or service role) is now checked against the new product. Tested locally. |

**Not tested by PGlite.** The local engine has one connection, so none of the concurrency behaviour above was exercised there; the single-connection checks cover only the sequential logic and the isolation-level guard.

**Automated, after applying (hosted):** `tests/db-capabilities/02-composition-concurrency.test.mjs`. Each parallel request is its own transaction on its own pooled connection. Scenarios repeat `CONCURRENCY_ROUNDS` times (default 10) and assert invariants. A pass is evidence, not proof, because race outcomes are not deterministic.

**Manual, deterministic two-session script (SQL editor or `psql`, development project only, after applying).** Replace the ids with a product and its organization created for the test.

1. Session 1: `begin; insert into public.product_materials (organization_id, product_id, custom_name, share_percent) values ('<org>', '<product>', 'one', 60);` (do not commit).
2. Session 2: `begin; insert into public.product_materials (organization_id, product_id, custom_name, share_percent) values ('<org>', '<product>', 'two', 60);` It **blocks**.
3. Session 1: `commit;`. Session 2 now fails with `23514` (total would be 120). `rollback;` in session 2. Expected final total: 60.
4. Repeat with updates: product with two rows of 40 percent; session 1 raises row A to 60 (uncommitted); session 2 raises row B to 60 and blocks; commit session 1; session 2 fails.
5. Archive race: session 1 `begin; update public.factories set archived_at = now() where id = '<factory>';` (uncommitted). Session 2: `insert into public.machines (organization_id, factory_id, name) values (...)` blocks; commit session 1; session 2 fails with `55000`.
6. Isolation guard: `begin isolation level repeatable read; insert ... product_materials ...;` fails with `25000`.

Note: sessions in the SQL editor run as the database owner, which bypasses RLS but still runs these triggers, so the script exercises exactly the trigger logic.

## M1.4B.1 corrective migration: account deletion under archived parents

Migration `20261022170000_allow_account_deletion_under_archived_parents.sql` (applied to the dev project after review; the two earlier migrations are unchanged).

- **Defect:** every `created_by` column is `on delete set null`. Deleting an account updates each row the user created. `private.enforce_active_parents` refused those updates under an archived factory or product (55000), so the deletion failed. All seven tables with the trigger were affected.
- **Fix:** an update under an archived parent is allowed only when `created_by` goes from a user id to NULL, that user's profile no longer exists, and every other column except `updated_at` is identical. Inserts, deletes and all other updates stay refused.
- **Hardening in the same function:** on UPDATE the OLD row's parents are checked as well as the new row's, so a privileged SQL caller cannot move a frozen row into an active parent. Not reachable through the API (`factory_id`, `product_id`, `organization_id` are insert-only).
- **No new privileges.** Manufacturers still have no privilege on `created_by`. The function keeps SECURITY DEFINER, `search_path = ''`, and no EXECUTE for PUBLIC, anon, authenticated or service_role.
- **Audit:** account deletion records one update per cleared row naming only `created_by`, with no actor and no values.
- **Remaining limits:** the sole owner of an ACTIVE company still cannot be deleted (foundation rule). A privileged caller who deletes a profile while bypassing the foreign key could then null attribution, which grants nothing beyond what that caller could already do.
- **Tests:** `tests/db-capabilities/03-account-deletion.test.mjs` (hosted, synthetic users).
